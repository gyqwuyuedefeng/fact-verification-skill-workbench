# 赛后 30 天落地计划

**参赛团队：** 火石验真官｜**成员：** 高永强、高翔宇、钱旭

## 落地方向

当前火石智能体已经具备模型调用、Agent 运行和 MCP 工具接入能力，但尚未形成面向 Skill 的通用治理体系，缺少不可变版本、同条件评测、发布门禁、影子灰度、晋升和回滚等能力。本次企业材料事实核验工作台以一个真实 Skill 跑通了最小闭环；赛后30天不再建设一个仅服务事实核验的专用平台，而是把已经验证的机制沉淀到现有火石智能体体系，并至少再接入一个不同业务目标的 Skill 验证复用性。

## 第 1—7 天：统一治理合同与项目边界

- 目标：明确通用 Skill 治理能力放在哪里、由谁消费，避免把比赛专用实现原样搬入现有系统。
- 动作：梳理 `ai-firelm`、`fd-universal-agent-pc`、`fd-universal-agent-pc-admin`、`kjjr-mcp-service` 和 `metastart` 的现状；统一 Skill 标识、版本状态、内容哈希、父版本、版本卡、评测绑定和发布记录等最小合同；选定第二个非事实核验 Skill 作为通用性试点。
- 分工：`ai-firelm` 承载 Agent 运行时、Skill 装载和版本选择；普通用户端只消费 Stable；管理端承载版本、评测、影子复核和回滚入口；MCP 与企业查询服务继续提供版本无关的工具和数据能力。
- 指标：五个项目的改造清单、接口责任人、数据迁移边界和第二 Skill 验收样本全部明确。
- 退出条件：Stable/Candidate 语义、评测口径或数据授权未统一，不进入开发和真实灰度。

## 第 8—14 天：落地通用版本与评测能力

- 目标：让不同 Skill 共用同一套注册、冻结、对照评测和发布门禁，而不是各自维护提示词和发布脚本。
- 动作：在火石智能体后台实现 DRAFT、CANDIDATE、STABLE、ARCHIVED 版本链和冻结内容哈希；运行时按明确版本加载 Skill；管理端提供版本卡、历史评测、按版本汇总、版本对比和单样本下钻；继续锁定同一数据、输入、模型参数、工具合同、证据快照和输出结构。
- 指标：事实核验 Skill 与第二试点 Skill 均可注册不可变版本；同条件评测可复跑且 Run Manifest 哈希一致；准确率、任务完成率、稳定性和人工介入率均有明确门禁。
- 退出条件：评测条件不可复现、冻结版本仍可被修改或历史记录会被覆盖时，不允许注册 Candidate。

## 第 15—21 天：接入通用影子灰度

- 目标：在不改变普通用户正式答案的前提下，让任意 Candidate 使用真实输入验证效果。
- 动作：`ai-firelm` 对授权请求执行 Stable 主运行和 Candidate 后台影子运行；`fd-universal-agent-pc` 始终只展示 Stable；`fd-universal-agent-pc-admin` 展示同一材料下的一致主张、差异主张、失败原因和人工 PASS/FAIL；MCP 与 `metastart` 保持工具能力和 Skill 版本解耦。
- 指标：影子完成率不低于 95%；普通用户收到 Candidate 结果的次数为 0；主体误配和无证据断言等硬失败为 0；每条差异均可追溯到输入、Skill 版本和证据快照。
- 退出条件：出现硬失败立即停止新影子并保留现场；影子异常不得影响 Stable 主运行。

## 第 22—30 天：完成晋升、回滚与第二 Skill 验收

- 目标：证明这套能力属于火石智能体，而不是企业事实核验 Skill 的专属功能。
- 动作：在管理端完成 Candidate 注册、开启/停止影子、人工复核、晋升和回滚；选择一个不同业务目标的 Skill，完整跑通数据准备、版本冻结、同条件评测、影子、晋升和回滚；输出通用接入说明、责任边界和审计记录，为后续 FireForge 和启玄 App 的高质量能力供给打基础。
- 指标：至少两个不同业务目标的 Skill 共用同一套治理链路；晋升后用户只消费新 Stable；完成一次可验证的回滚演练；版本、评测、影子和发布历史均为追加记录且可审计。
- 退出条件：第二 Skill 需要复制一套专用治理代码、不能安全回滚或未通过业务人工复核时，不按时间节点强行晋升。
